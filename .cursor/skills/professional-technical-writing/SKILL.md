# Professional Technical Writing

## 1. 写作定位

所有技术文档应采用专业、严谨、准确的工程技术写作风格。

文档面向具有相应技术背景的开发人员、架构人员和工程管理人员。表达应以技术事实、系统职责、设计约束、实现机制和工程关系为核心。

写作目标是准确传达技术内容，而不是通过修辞、口号或形式化总结制造专业感。

基本要求：

- 使用准确的专业技术名词。
- 使用完整、明确的技术表述。
- 保持客观、克制的叙述口吻。
- 清楚说明模块职责、处理机制和依赖关系。
- 保持术语、概念和上下文的一致性。
- 避免口语化、宣传化、情绪化和套路化表达。
- 不得为了追求流畅而牺牲技术准确性。
- 文档内容必须与当前代码实现及实际系统行为保持一致。

## 2. 专业化表达

### 2.1 使用专业技术术语

优先使用行业内具有明确含义的技术名词，不使用含糊的日常表达替代专业概念。

例如：

| 不推荐表达 | 推荐表达 |
|---|---|
| 把任务分发出去 | 任务调度与执行分配 |
| 把数据统一起来 | 数据标准化与模型映射 |
| 检查一下有没有问题 | 执行规则检测并生成检测证据 |
| 处理失败的情况 | 异常处理与失败恢复 |
| 各个模块互相配合 | 模块间接口协作与数据交互 |
| 让系统跑起来 | 完成服务部署及运行环境初始化 |
| 把结果存下来 | 持久化检测结果及关联证据 |

专业术语必须符合具体上下文，不得为了显得专业而堆砌缩写、英文单词或不必要的概念。

### 2.2 明确技术主体和职责

句子应明确说明由哪个模块、组件或机制执行什么操作。

避免使用缺少明确主体的表达，例如：

- “通过这种方式就可以实现……”
- “这里主要是为了……”
- “整体上会比较方便……”
- “相关内容需要进行处理……”

应当直接说明具体模块的职责、处理对象和产生的结果。

### 2.3 使用准确的技术动词

优先使用具有明确工程语义的动词，例如：

- 创建、维护、调度、分配、执行。
- 采集、解析、识别、匹配、规范化。
- 校验、验证、过滤、转换、归并。
- 持久化、索引、查询、更新、发布。
- 关联、追踪、恢复、回滚、隔离。
- 授权、认证、审计、限制。

避免反复使用“处理”“完成”“实现”“支持”等泛化动词，却不说明实际操作内容。

## 3. 禁止 AI 化表达

技术文档不得出现明显的生成式 AI 套路和模板化句式。

### 3.1 禁止口号式表达

避免使用缺少实际技术信息的总结性表达，例如：

- “打造完整的技术闭环。”
- “构建强大的能力体系。”
- “实现全面升级。”
- “为后续发展奠定坚实基础。”
- “提升系统整体能力。”
- “形成高效、稳定、可靠的架构。”

如果确实需要表达某项工程收益，应说明具体机制及其作用，不得以抽象口号替代技术说明。

### 3.2 禁止机械化对照句式

避免反复使用以下句式：

- “不是……而是……”
- “不仅……还……”
- “既……又……”
- “不再……而是……”
- “从……转变为……”
- “并非……而是……”

这些句式在必要时可以使用，但不得成为全文主要组织方式。

尤其禁止通过连续的否定和转折制造所谓的观点深度。

应直接陈述架构职责、技术选择和约束条件。

### 3.3 禁止口语化表达

技术文档中避免使用：

- “我们可以看到”
- “这里需要注意”
- “简单来说”
- “说白了”
- “实际上就是”
- “把它搞定”
- “跑起来”
- “兜底”
- “做一层封装”
- “后面再处理”

除非属于明确的代码注释、交互说明或必要的用户操作指引，否则不应使用聊天式表达。

### 3.4 禁止套路化总结

避免在每个章节末尾机械添加“本节总结”“核心价值”“最终效果”等内容。

不要重复前文已经说明的结论，也不要为了章节完整而添加没有新信息的总结段落。

章节结尾应自然结束于最后一项实际技术内容。

### 3.5 禁止虚构技术深度

不得使用大量术语掩盖缺乏实际设计的内容。

以下情况均不符合要求：

- 只罗列技术名词，不说明其在系统中的职责。
- 将普通函数调用描述为复杂的架构机制。
- 使用“智能化”“自动化”“高性能”等词语，却没有对应实现机制。
- 将尚未确定的技术方案描述为已经确定的设计。
- 用抽象概念替代必要的接口、数据流和执行过程说明。

## 4. 技术文档组织方式

文档应根据内容建立清晰的层次关系，优先采用从整体到局部的组织方式。

对于架构和技术设计文档，通常按照以下逻辑展开：

1. 项目背景及建设目标。
2. 系统定位和整体架构。
3. 核心模块及其职责。
4. 模块之间的接口和数据流。
5. 核心机制与关键处理流程。
6. 技术栈及选型依据。
7. 运行约束、兼容性和质量要求。

具体章节应根据实际项目内容调整，不得机械套用固定目录。

### 4.1 先说明整体关系

介绍一个系统或模块时，先说明它在整体架构中的位置、承担的职责以及与其他模块的关系。

随后再介绍内部组成、关键机制和实现约束。

不得在缺少整体背景的情况下，直接堆积大量类名、接口名和实现细节。

### 4.2 明确模块职责

每个模块应说明：

- 模块的主要职责。
- 处理的数据或对象。
- 对外提供的接口或能力。
- 依赖的其他模块。
- 产生的结果及其使用方。

对于存在边界关系的模块，应明确职责划分，避免不同章节反复描述相同内容。

### 4.3 说明处理流程

涉及任务调度、数据处理、扫描执行、规则检测和状态管理等内容时，应说明关键处理顺序。

流程描述需要交代输入、处理环节、关键判断和输出结果。

不能只使用“经过处理后得到结果”一类概括性句子。

### 4.4 合理使用表格和列表

表格适用于技术选型比较、模块职责划分、接口分类和数据类型说明。

列表适用于并列的功能、约束或检查项。

对于具有因果关系和连续执行顺序的内容，应使用完整段落解释，不能将所有内容拆成碎片化列表。

不要为了追求排版形式而将简单内容制作成表格。

## 5. 流程图与技术图示规范

流程图、架构图、时序图和数据流图属于技术文档的一部分，必须准确表达系统结构和实际执行过程。

图示应当具有明确的技术用途，能够帮助读者理解模块关系、执行顺序、状态变化或数据流向。不得为了增加文档的视觉内容而绘制缺乏实际信息的示意图。

### 5.1 图示类型与适用范围

根据需要表达的技术内容选择图示类型：

| 图示类型 | 主要用途 |
|---|---|
| 架构图 | 描述系统分层、模块组成、部署关系和依赖边界 |
| 流程图 | 描述业务处理顺序、判断条件和执行分支 |
| 时序图 | 描述多个组件之间的调用顺序、请求响应及异步交互 |
| 数据流图 | 描述数据来源、传递路径、转换过程和存储位置 |
| 状态图 | 描述对象生命周期、状态转换及转换条件 |
| 部署图 | 描述运行节点、进程、网络边界和部署依赖 |

不得用一种图示形式表达所有类型的技术关系。例如，模块之间的静态依赖不应全部绘制为执行流程，具有时间顺序的交互也不应仅使用普通架构图代替。

### 5.2 流程图结构

流程图应当具有明确的起点、处理节点、判断节点和终点。

绘制时遵循以下要求：

- 明确流程的触发条件和输入。
- 按照实际执行顺序组织节点。
- 判断节点必须表达明确的判断条件。
- 判断分支应标注具体结果，例如“校验通过”“校验失败”。
- 不同分支应连接到真实存在的后续处理环节。
- 流程结束节点应对应实际完成、失败、取消或等待状态。
- 对异步任务、重试和循环处理，应明确表达其返回路径及退出条件。
- 对重要的异常路径，应展示异常处理和资源清理过程。

不能将所有流程简化为连续的矩形节点，也不能使用“处理”“执行”“判断”等没有具体语义的节点名称。

### 5.3 判断与分支

判断节点应描述可验证的条件，而不是模糊的业务意图。

例如：

- 不推荐：`是否正常？`
- 推荐：`TCP 连接是否建立成功？`
- 不推荐：`检查结果`
- 推荐：`目标地址是否属于授权范围？`

每个判断节点的输出分支应当具有明确语义。

如果判断存在多个结果，应完整展示主要分支，不能只画出成功路径而省略失败路径。

对于不适用、证据不足、超时和执行失败等不同状态，应根据实际业务语义分别表达，不得将其合并为含义模糊的“失败”。

### 5.4 模块边界与交互关系

架构图和数据流图必须体现真实的模块边界。

- 使用边界框表示具有明确归属的模块、服务或运行环境。
- 区分进程内调用、跨进程通信和外部服务交互。
- 连接线应表示真实的数据传递、调用或依赖关系。
- 对请求、响应、事件和数据持久化等不同关系，应使用清晰的标注。
- 不得将不存在直接调用关系的模块绘制为直接调用。
- 不得混淆控制流、数据流和静态依赖关系。

图中出现的模块名称、接口名称和领域对象应与正文及代码中的实际定义保持一致。

### 5.5 异常路径与复杂流程

对于涉及资源分配、网络通信、任务调度、事务处理和状态管理的流程，应考虑异常及恢复路径。

重点检查：

- 超时和取消。
- 外部依赖不可用。
- 输入或权限校验失败。
- 部分执行成功。
- 重试及重试终止条件。
- 资源释放与状态恢复。
- 重复执行和幂等处理。

不要求每张图都包含所有异常细节。应根据图示目的确定表达范围，并在正文中补充图示无法清晰容纳的处理规则。

### 5.6 Mermaid 与图示语法

使用 Mermaid 绘制流程图、时序图和架构图时，应遵循其标准语法。

- 使用明确且稳定的节点 ID。
- 节点文本应简洁、准确，避免长段落。
- 复杂判断拆分为多个有明确含义的判断节点。
- 使用子图表示模块或系统边界。
- 使用连线文字标注分支条件和交互含义。
- 避免不必要的交叉连线。
- 避免节点数量过多导致图形难以阅读。
- 对较大的流程按职责或处理阶段拆分成多张图。

Mermaid 图示必须保证语法有效，提交前应检查渲染结果。不能只检查代码块是否完整，还需要确认节点、连线、标签和布局能够正确呈现。

对于无法通过 Mermaid 清楚表达的复杂架构关系，可以采用其他适合的标准图示工具，不应为了统一格式而牺牲图示可读性。

### 5.7 图文一致性

图示与正文必须表达同一套设计。

- 正文中出现的重要模块，应与架构图保持一致。
- 图示中的执行顺序，应与正文描述的实际流程一致。
- 图示中的接口和组件名称，应与代码及接口文档保持一致。
