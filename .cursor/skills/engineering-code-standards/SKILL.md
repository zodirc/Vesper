# Engineering Code Standards

1. 基本原则

代码开发必须遵循工程化规范，以正确性、完整性、可维护性和健壮性为基本要求。

开发工作不能仅以代码能够运行或局部功能能够演示作为完成标准。必须结合需求、设计文档和现有工程约束，完成完整的功能实现、模块集成、异常处理及必要验证。

遵循以下原则：

设计一致性： 严格遵循项目需求、架构设计、技术设计和接口契约，不得擅自改变既定设计。

实现完整性： 完成需求涉及的全部功能路径，不得只实现主流程而遗漏必要的辅助逻辑、异常处理和模块集成。

工程一致性： 遵循项目已有的代码组织、命名、错误处理、日志和测试规范。

可维护性： 代码应具有清晰的职责边界、合理的抽象层次和明确的数据流。

健壮性： 对异常输入、资源限制、并发行为、外部依赖失败及边界条件进行合理处理。

可验证性： 实现结果必须经过适当的测试、检查和实际执行验证。

2. 开发文档遵循要求

开发前必须检查与当前任务相关的需求文档、架构文档、技术设计文档、接口定义及已有实现。

开发文档是实现依据，不得将其视为参考性建议。

2.1 设计约束

按照文档定义的模块职责、接口契约、数据结构和调用关系实现。

不得为了缩短实现时间而跳过文档中规定的功能。

不得擅自删除设计中要求的校验、状态管理、异常处理或兼容性逻辑。

发现设计存在冲突、歧义或不可实现之处时，应明确指出具体问题及影响，不得自行选择一个方便实现的方案并将其视为既定设计。

如果现有代码与设计文档不一致，应先判断差异来源和影响范围，再决定修改方式。

2.2 完整性检查

实现过程中应将设计要求转换为可核对的工作项，并逐项确认：

必须实现的功能是否全部完成。

所有规定的接口是否已经实现并正确接入。

数据是否经过完整的创建、读取、更新和必要的清理流程。

正常流程、异常流程和边界条件是否得到处理。

模块之间的调用关系和数据传递是否完整。

配置、权限、日志和错误处理是否符合设计要求。

必要的测试是否已经编写并执行。

不得将只完成核心路径、仅实现部分接口或暂时返回固定结果的代码认定为完整实现。

3. 代码注释规范

代码注释应采用标准化、结构化的文档注释格式。对于支持 Doxygen 风格注释的语言，统一采用 @brief、@param、@return、@throws 等标签。

注释应描述接口职责、参数语义、返回值、异常条件及必要的使用约束，不应重复代码本身已经明确表达的信息。

3.1 函数与方法注释

公开函数、公共接口、复杂方法以及具有重要业务语义的内部函数，应提供完整的文档注释。

采用以下结构：

@brief：简要描述函数的职责。

@param：描述参数含义、输入要求及必要约束。

@return：描述返回值及其语义。

@throws：描述可能抛出的异常或错误条件，按语言和项目规范使用。

@note：补充重要限制、调用约束或实现注意事项。

@warning：标注可能造成资源、数据或安全影响的行为。

注释内容应准确对应实际实现，不得描述尚未实现或无法保证的行为。

3.2 类、结构体与接口注释

对具有明确职责的类、结构体和接口，应使用 @brief 说明其用途及在系统中的职责。

必要时说明：

对象负责管理的资源。

生命周期和初始化要求。

线程安全及并发访问约束。

与其他模块的关系。

状态变化及调用限制。

3.3 注释质量

禁止以下注释方式：

仅将函数名翻译成自然语言。

重复解释每一行显而易见的代码。

使用含糊描述，例如“处理数据”“执行相关操作”。

描述与实际实现不一致的行为。

保留已经失效的注释。

使用注释掩盖不合理的代码结构。

注释应解释设计意图、约束条件和非直观行为。对于复杂算法、状态转换、协议处理和安全校验，应说明关键判断依据。

3.4 注释示例

文档注释使用中英双语。同一标签下先写中文，再写英文。两种语言表达同一语义，信息量保持一致。不得只保留其中一种语言，也不得让两种表述出现含义差异。

/**
 * @brief 建立到指定远端端点的连接。
 *        Establishes a connection to the specified remote endpoint.
 *
 * @param address 远端端点地址。
 *                Remote endpoint address.
 * @param port 远端端点端口，必须位于有效端口范围内。
 *             Remote endpoint port. Must be within the valid port range.
 * @param timeout 建立连接允许的最长时间。
 *                Maximum time allowed to establish the connection.
 * @return 成功时返回连接句柄。
 *         Connection handle on success.
 * @throws ConnectionError 无法建立连接时抛出。
 *                         Thrown if the connection cannot be established.
 *
 * @note 调用方负责释放返回的连接。
 *       The caller is responsible for releasing the returned connection.
 */
Connection connect(const Address& address,
                   uint16_t port,
                   Duration timeout);

Go 使用文档注释表达相同内容。导出标识符的中文说明和英文说明连续书写，参数、返回值、错误条件和调用约束与上述标签对应。

// Connect 建立到指定远端端点的连接。
// Connect establishes a connection to the specified remote endpoint.
//
// address 为远端端点地址。
// address is the remote endpoint address.
//
// port 为远端端点端口，必须位于有效端口范围内。
// port is the remote endpoint port and must be within the valid port range.
//
// timeout 为建立连接允许的最长时间。
// timeout is the maximum time allowed to establish the connection.
//
// 成功时返回连接句柄。调用方负责释放返回的连接。
// On success, it returns a connection handle. The caller is responsible for releasing the returned connection.
//
// 无法建立连接时返回 ConnectionError。
// It returns ConnectionError if the connection cannot be established.
func Connect(address Address, port uint16, timeout Duration) (Connection, error)

不同语言可以采用符合其工具链的等价注释语法，但标签语义、双语要求和文档完整性要求保持一致。

4. 代码可读性与结构规范

代码应优先保证职责清晰、控制流明确和逻辑易于追踪，不得以过度抽象或过度压缩代码换取表面上的简洁。

4.1 职责划分

函数应围绕明确的职责组织。

避免单个函数同时承担输入解析、业务判断、数据修改、外部调用和结果输出等多个不相关职责。

模块之间通过明确的接口交互，避免不必要的隐式依赖。

公共接口应保持稳定，内部实现细节不应无必要地暴露。

对重复逻辑进行合理抽象，但不得为了消除少量重复而引入复杂的通用框架。

4.2 命名规范

变量、函数、类型、接口和常量应使用能够表达业务含义的名称。

禁止使用缺乏语义的缩写、无意义的单字符命名及容易混淆的名称。循环索引等具有明确局部语义的变量除外。

命名应遵循项目已有约定，不得在同一模块中混用多种命名风格。

4.3 控制流与状态管理

避免不必要的嵌套和复杂条件表达式。

状态转换应具有明确的入口、出口和合法性约束。

对关键状态变化，应保证数据更新和相关操作的一致性。

不得通过大量布尔标记掩盖复杂的状态模型。

对异步操作、并发访问和任务取消，应明确状态归属及资源生命周期。

4.4 代码组织

代码应按照模块职责组织，避免将不相关功能集中在同一文件或类型中。

公共接口、业务逻辑、基础设施适配和平台相关实现应保持合理边界。平台差异应集中处理，避免在业务代码中散布大量平台判断。

5. 代码健壮性要求

健壮性是功能实现的一部分，不属于可选的后续优化。

5.1 输入与边界校验

对外部输入、配置、网络响应、文件内容和跨模块数据进行必要校验。

重点处理：

空值、缺失字段和非法格式。

数值范围和长度限制。

非法状态及不支持的操作。

数据类型不匹配。

超大输入和异常响应。

编码、路径和协议边界条件。

校验应放置在合理的信任边界，避免重复校验造成逻辑混乱，也不得因调用方通常传入合法数据而完全省略必要检查。

5.2 错误处理

错误必须具有明确语义，能够定位失败环节。

不得无条件忽略错误返回值。

不得使用空异常处理或无意义的默认值掩盖失败。

对可恢复错误、不可恢复错误和业务拒绝进行合理区分。

错误向上传递时，应保留必要的上下文。

日志不得泄露密码、密钥、令牌及其他敏感数据。

5.3 资源管理

对文件、网络连接、锁、数据库事务、子进程和其他系统资源，应明确其所有权和释放时机。

需要考虑：

正常结束时的资源释放。

异常退出时的清理。

超时和取消时的资源回收。

并发访问时的资源竞争。

文件描述符、连接数、内存和线程等资源上限。

5.4 并发与异步处理

涉及并发或异步执行时，应明确共享状态、同步方式和生命周期。

重点检查数据竞争、死锁、重复执行、任务泄漏、取消失效和资源竞争等问题。

不得将增加并发数量作为性能优化的唯一手段，应同时考虑目标系统承载能力及资源预算。

5.5 外部依赖

网络服务、数据库、文件系统、操作系统接口和第三方组件均可能失败。

应合理处理超时、连接中断、响应异常、版本不兼容和部分成功等情况。对于可能产生副作用的操作，应明确重试条件，避免重复执行导致数据或业务状态异常。

6. 实现完整性与禁止半成品

开发任务必须形成完整的实现闭环。

以下情况不得认定为完成：

只实现核心功能，遗漏辅助流程。

只实现接口定义，未完成实际处理逻辑。

只完成调用方或被调用方其中一侧。

使用 TODO、FIXME、占位返回或固定数据替代实际实现。

将必要的错误处理、状态管理和数据持久化留给后续工作。

新增模块后没有接入原有系统。

修改接口后没有同步更新相关调用方、测试和文档。

仅通过编译，没有验证实际行为。

如果任务范围过大，无法在当前工作中全部完成，应明确说明未完成的部分、依赖条件和影响范围，不得将部分完成描述为整体完成。

7. 测试与验证

代码提交前必须根据修改范围执行相应验证。

验证范围至少应覆盖：

编译、构建或静态类型检查。

单元测试。

关键模块集成测试。

正常输入和异常输入。

边界条件。

接口兼容性。

关键资源及状态管理。

修改涉及的历史功能回归。

测试不能仅以覆盖率或测试数量作为质量标准，应关注实际行为是否符合需求和设计。

如果测试无法执行，必须说明具体原因、未验证范围和潜在风险，不得声称验证通过。

8. 开发完成标准

任务完成前，必须进行一次对照检查：

对照需求和设计文档，确认所有要求均有对应实现。

检查新增及修改的接口是否完整接入。

检查异常处理、资源释放和边界条件。

检查注释、命名、代码结构和可读性。

检查测试是否覆盖本次修改的关键行为。

检查是否存在占位实现、未处理 TODO 或临时绕过逻辑。

检查相关文档和调用方是否同步更新。

最终交付说明应区分已完成内容、验证结果和未完成事项。只有实际完成并经过相应验证的内容，才能标记为完成。
